## 마일스톤과 일정 판단

### D3 — 실제 저장과 권한

UI가 덜 예뻐도 실제 DB에 저장하고 두 사용자가 팀에 들어올 수 있어야 한다. Mock 데이터만 있다면 미통과다. Docker가 장애물이면 환경 문제를 기록하고 개발 전용 hosted Supabase 사용 가능성을 검토한다. 실제 외부 프로젝트 생성·설정은 사용자에게 필요한 계정 작업을 구체적으로 알려준다. 권한 검증을 생략하는 대체는 하지 않는다.

D3까지 못 끝냈으면 D9 멘션 자동완성과 D13 공개 배포를 먼저 제외한다. 로그인·팀 역할의 핵심 문제를 화면 장식으로 덮지 않는다.

### D7 — 면접 소재가 되는 협업

다른 계정 두 개에서 카드가 동기화되고, 같은 version에 대한 두 수정 중 한쪽이 충돌해야 한다. D7에 아직 이 조건을 충족하지 못하면 D8 시간을 먼저 여기에 사용한다. OAuth 외부 설정이 막혔어도 개발 사용자 2명으로 검증을 계속한다.

D9 범위 판단(2026-09-23): D8 기록·실제 코드에서 멘션/알림을 제외해야 할 필수 대형 결함은 확인되지 않아 일반 텍스트 댓글·멤버 선택 멘션·인앱 알림을 유지했다. 자동완성·풍부한 텍스트·이메일/푸시는 추가하지 않았다. 실제 실행 결과와 중간 결함은 TEST_REPORT에 남긴다.

### D10 — 기능 동결

2026-09-24 D10 URL 구현으로 신규 기능을 동결했다. 기존 기능의 결함·접근성·회귀·실행 재현·문서에 집중한다. 미구현 `/demo` 신규 화면은 후속으로 옮기고 D13 샘플 시연은 기존 합성 계정의 실제 앱을 사용한다. 초대·댓글·멘션·알림 범위는 유지한다. P1 축소를 했다면 ACCEPTANCE와 README에 즉시 반영한다. D11 이후 “AI 기능 하나만 추가” 같은 범위 확대를 하지 않는다.

### D14 — 제출 가능한 상태

검증하지 못한 기능은 명시한다. 필수 데이터 무결성·권한·핵심 흐름이 실패하면 릴리스 후보 상태로 남기고 “MVP 완성”으로 소개하지 않는다. 화면이 예쁜 것과 협업 기능이 검증된 것은 각각 확인한다.

## 하루 진행 순서

1. PROGRESS의 현재 단계와 미해결 결함을 읽는다.
2. 해당 P 프롬프트 실행. 구현자에게 해당 범위까지만 완료하도록 한다.
3. V 프롬프트 실행. 가능하면 새 대화에서 실제 코드와 환경으로 확인한다.
4. 실패 시 R01로 수정하고 관련 항목만 다시 검증한다. 이후 단계의 전제를 깨는 결함은 먼저 해결한다.
5. 직접 조작하고 화면/로그를 저장한다. 실제 확인하지 않은 결과는 NOT_RUN.
6. PROGRESS에 5~10줄, 중요한 결정이 있으면 DECISIONS에 기록한다.
7. 일관된 변경 단위로 로컬 커밋. push·공개 배포 여부는 현재 사용자 지시에 따른다.

## 2시간/일밖에 없다면

14일 약 28시간에는 원안 전체를 약속하지 않는다. 다음을 최소 범위로 재계획한다: 개발용 두 사용자 계정, 고정 팀·역할, 버그 양식, 보드, 상태 이동, 버전 충돌, 낙관적 이동·실패, 재연결, 기본 검색, 테스트·README. 초대 UI·OAuth 실연동·멘션/알림·공개 배포는 후속으로 옮긴다. 이 경우에도 최소 1주 정도 추가 여유를 권한다. 소셜 로그인·알림이 빠진 사실을 공개한다.
