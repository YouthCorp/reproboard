# 로컬 Codex 실행 프롬프트

이 파일을 프로젝트의 `docs/planning/PROMPTS.md`로 복사한다. 각 코드 블록을 하나씩 실행한다. 아래 지침은 현재 저장소의 기존 지침·사용자 승인·도구 권한을 존중하며 권한 우회 옵션을 사용하지 않는다.

## 사용 규칙

- 처음 한 번 P00, 이후 P01→V01→P02→V02 순서다. P는 구현, V는 검증이다.
- P 결과에서 “완료”라고 해도 V에서 실제 코드·실행 결과를 확인한다. 새 검증 대화에서 시작하면 아래 V00을 먼저 붙인다.
- P와 V 모두 해당 단계의 변경에 필요한 검증만 한다. 최종 전체 회귀는 D12에 한다.
- V의 PASS는 실행한 범위에만 적용한다. 브라우저·Docker·OAuth 설정이 없으면 NOT_RUN과 수행 방법을 남긴다.
- 다음 단계의 전제를 깨는 결함이 있으면 R01로 고친 뒤 관련 검증을 다시 실행한다.

## P00 — 시작·공통 작업 계약

```text
너는 이 로컬 저장소에서 ReproBoard를 구현하는 프론트엔드 개발자다. 목표는 14일 약 70시간 범위에서 공개 가능한 포트폴리오 MVP를 완성하는 것이다.

먼저 기존 AGENTS.md와 git 상태를 확인하고 사용자 변경을 보존해라. docs/PRD.md, docs/ARCHITECTURE.md, docs/ACCEPTANCE.md, docs/PROGRESS.md, docs/planning/ROADMAP.md를 읽어라. 없는 파일은 누락을 알려주고 제공된 키트가 다른 위치에 있는지 확인해라. 실제 코드를 읽기 전 구현된 것으로 가정하지 마라.

현재 OS·셸·Node·패키지 매니저·Docker·Supabase CLI·브라우저 실행 가능 여부를 확인해라. 비밀 값을 출력하지 마라. 새 환경에서는 호환되는 안정 버전을 공식 문서로 확인하고 버전을 고정해라. 기존 프로젝트 지침에 맞춰라.

앞으로 모든 구현 단계는 실제 파일 변경, 관련 검증, 짧은 진행 기록까지 수행한다. TanStack Query는 서버 데이터, Zustand는 공유 임시 UI, URL은 검색·필터·정렬·상세 선택을 맡긴다. 제품 조건·권한·version 검사는 DB에서 강제한다. Realtime는 재조회 신호이며 데이터의 기준은 서버다.

불필요한 확인 질문 없이 허용된 로컬 구현을 진행해라. 외부 계정 설정이 필요한 부분은 정확한 사용자 작업을 한 번에 정리하고 가능한 로컬 작업을 계속해라. 기존 허가가 없는 운영 변경·외부 공개는 임의로 하지 마라. 사용자 지시나 기존 승인이 있으면 반복 승인을 요구하지 마라.

기술 사례는 중요한 결정 3건 중심으로 남기고 단계당 진행 기록은 5~10줄로 제한한다. 테스트·캡처·성과·사용자 피드백은 실제로 확인한 것만 적어라. 각 종료 보고에는 변경 결과, 실행 결과와 NOT_RUN, 남은 결함, 핵심 파일, 내가 직접 확인할 3개 행동과 이해할 개념 1개를 포함해라.

지금은 환경·범위·선행 조건을 확인하고 docs/PROGRESS.md를 초기화해라. 현재 구현된 코드가 있으면 완료 단계를 추정하지 말고 근거로 매핑해라. 다음 실행 프롬프트를 지정해라.
```

## V00 — 새 검증 대화의 공통 계약

```text
너는 현재 ReproBoard 단계의 검증자다. AGENTS.md, docs/PRD.md, docs/ARCHITECTURE.md, docs/ACCEPTANCE.md와 현재 단계의 실제 변경을 읽어라. 이전 대화의 “완료” 보고를 증거로 사용하지 마라.

검증 프롬프트가 지정한 위험을 실제 실행으로 확인해라. 결과는 PASS/FAIL/NOT_RUN이며 실행 명령·환경·재현 절차·기대/실제 결과를 docs/TEST_REPORT.md에 짧게 남겨라. 환경 미지원은 PASS가 아니다. 테스트가 같은 구현의 결과를 그대로 정답으로 삼고 있지 않은지도 확인해라.

이 검증 단계에서는 원칙적으로 코드 수정을 하지 말고 결함과 최소 수정 범위를 제시해라. 재현용 테스트·증거 파일 추가는 가능하다. 관련 없는 전면 리팩터링이나 선택 기능 추가를 요구하지 마라. 다음 단계 진행 가능 여부와 실제로 확인하지 못한 항목을 구분해라.
```

## D2

### P02 — 실제 DB까지 연결되는 최소 흐름

```text
PRD/ARCHITECTURE를 기준으로 D2를 구현해라. 핵심 테이블과 이후 확장이 가능한 최소 migration을 작성하고 RLS·grant를 함께 설정해라. workspace/membership, issues, activity_events, command_receipts부터 구현하고 나머지는 필요 단계에서 추가해도 된다.

개발 전용 계정·합성 팀을 로컬에 준비하고, 실제 로그인 사용자 세션으로 제목만 있는 Inbox 이슈 생성→조회→제목 수정 흐름을 얇은 화면까지 연결해라. 클라이언트의 직접 table 쓰기는 차단하고 RPC에서 auth.uid·팀 권한·허용 필드를 검사해라.

issue version 검사, requestId 중복 방지, 실제 변경과 activity/receipt의 단일 트랜잭션을 이 최소 흐름에 넣어라. 동일 requestId/다른 payload는 거부한다. 테이블·함수 이름을 스키마로 한정하고 필요한 execute 권한만 허용해라. SECURITY DEFINER가 있다면 실제 권한 검사를 누락하지 마라.

타팀·Viewer 쓰기 거부, 두 동시 수정의 version 경합, 명령 재전송을 실제 DB로 확인해라. .env와 로컬 seed 초기화 보호 조건을 마련하고 실행한 migration·타입 생성 절차를 기록해라.
```

### V02 — DB가 실제 기준인지 검증

```text
D2를 검증해라. 화면 조작이 실제 DB에 반영되고 새로고침 후 유지되는지 확인해라. 서비스 키가 아닌 일반 사용자 세션으로 읽기/명령이 실행되는지 조사해라.

직접 issues insert/update를 시도하고 거부를 확인해라. 같은 version을 사용한 두 수정 요청은 성공 1건·충돌 1건인지, 같은 requestId의 동시 재전송은 한 번만 반영되는지 확인해라. 권한 거부 시 변경·성공 activity·receipt가 잘못 남지 않는지 검사해라.

로컬 DB 초기화부터 migration 재적용을 확인하되 대상이 로컬 개발 DB인지 먼저 확인해라. 재현 스크립트·실제 명령·결과를 남기고 UI mock만 통과한 결과를 DB 검증으로 적지 마라.
```

## D3

### P03 — 로그인·팀·권한

```text
D3를 구현해라. Supabase Auth의 현재 공식 Next.js/GitHub 로그인 문서를 확인하고 GitHub OAuth 1종, 콜백, 로그아웃, 세션 만료 안내를 구성해라. 외부 OAuth 설정이 없다면 필요한 앱 등록/콜백/환경 변수 작업을 정확히 알려주고 로컬 개발 사용자로 기능 개발을 계속해라.

워크스페이스 생성자 Owner, Owner의 Member 초대 링크 생성, 로그인 사용자의 초대 수락, Member↔Viewer 변경 UI를 만들어라. 초대는 24시간·1회 사용·서버 저장 해시·역할 고정이며 동시에 수락해도 한 사람만 가입한다. Owner 자가 강등·이전은 지원하지 않는다.

권한표를 읽기/쓰기/검증/댓글/초대/역할 변경과 타팀 접근에 적용해라. 프로필은 같은 팀의 표시 이름만 필요한 만큼 제공한다. 비회원 id 주입·멤버십 정책 재귀·임의 owner 지정 경로를 막아라. 기본 개발 계정 3명과 별도 팀 사용자로 실제 접근 검증을 만들고 기록해라.
```

### V03 — 권한 우회·참여 흐름 검증

```text
D3를 검증해라. Owner·Member·Viewer·별도 팀·로그아웃 상태 각각의 실제 세션으로 PRD 권한표를 실행해라. UI 버튼 외에 RPC와 table endpoint 직접 요청으로 확인한다. 타팀 workspaceId/issueId/userId를 payload에 넣고 격리가 유지되는지 확인해라.

초대 정상·만료·재사용·동시 수락, Member의 초대/역할 변경 시도, Owner 자가 강등을 확인해라. 현재 구현된 프로필 쿼리가 팀 외 정보를 주지 않는지도 확인한다. 알림 접근 검증은 알림 구현 단계 D9에서 수행한다. GitHub OAuth 정상/취소는 실제 설정이 있을 때 수동으로 검증하고 개발 사용자 로그인과 구분해라.

권한 누출이 있으면 다음 단계 전에 해결할 결함으로 표시하고 최소 수정 지점을 제시해라. 로컬 reset/seed가 외부 DB에 실행될 수 없는지도 확인해라.
```

## D4

### P04 — 보드·상세·구조화 입력

```text
D4를 구현해라. 실제 Query 캐시에서 5개 고정 상태의 보드와 상세 패널을 렌더링하고 생성/편집 폼을 연결해라. PRD의 필드·기본값·길이·공백 규칙을 준수하고 제목만으로 Inbox 등록이 가능하게 해라.

재현 단계·기대/실제 결과·환경의 충족 수와 누락 항목을 보인다. 충족 수를 신뢰도나 재현 성공률이라고 표현하지 마라. severity와 priority의 의미를 도움말로 구분한다. 저장 전 로컬 입력과 서버 값을 분리하고 원격 재조회로 입력이 사라지지 않게 해라.

보드/상세는 같은 서버 데이터 소유자를 사용한다. 로딩·0건·오류·재시도·권한 없음, 긴 제목, 한글 IME, 모바일 상세, 폼 오류의 라벨·포커스를 구현해라. 생성/편집은 실제 DB로 검증하고 캡처 2장을 남겨라. DnD와 부가 애니메이션은 아직 하지 마라.
```

### V04 — 폼·실제 데이터·상태 경계 검증

```text
D4를 검증해라. 빈 값·공백·최대 길이·한글 조합 입력·긴 제목·잘못된 담당자에 대해 기대 동작을 확인해라. 생성→편집→새로고침→재진입이 실제 DB와 일치하는지 본다.

편집 중 데이터 재조회가 입력을 덮어쓰는지, 같은 이슈 데이터가 Query/Zustand/로컬 state에 중복 소유되는지 확인해라. 0건·로딩·조회 실패·권한 없음·390px 화면에서 복구 가능한 화면인지 실제로 조작해라. 버그는 재현 순서·기대/실제를 남겨라.
```

## D5

### P05 — 트리아지·재검증 상태 규칙

```text
D5를 구현해라. PRD 상태 전환 표와 상태별 필수 조건을 순수 함수와 DB 명령에 구현해라. Ready 전에 재현 필드·재현 상태·분류를 검사하고 In Progress에는 유효 담당자, Verify에는 수정 메모·앱 버전을 요구해라.

Verify→Done은 현행 expectedVersion에 대한 통과 검증 기록과 상태 전환을 한 트랜잭션으로 수행한다. Verify→In Progress에는 실패 기록·이유, Done→Inbox에는 재오픈 사유를 요구하고 과거 기록을 보존한다. 직접 편집으로 현재 상태의 필수 정보를 지울 수 없게 해라. Done의 본문은 재오픈 후 수정한다.

먼저 상태 이동 메뉴와 필요한 입력 다이얼로그로 전체 흐름을 완성해라. 실패·취소 시 상태가 바뀌지 않도록 해라. 허용/금지 전환, 필드 편집 우회, 오래된 version의 검증 요청을 테스트하고 제품 흐름 캡처를 남겨라.
```

### V05 — 완료 조건의 서버 검증

