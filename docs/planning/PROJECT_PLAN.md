# ReproBoard 프로젝트 계획

상태: 계획 · 기준일: 2026-09-13 · 목표: 프론트엔드 취업 포트폴리오용 2주 MVP

## 1. 제품 정의

**3~8명 규모 개발팀을 위한, 재현 정보와 재검증 결과가 연결되는 버그 트리아지 보드.**

트리아지는 들어온 버그를 확인하고, 지금 처리할지·얼마나 급한지·누가 맡을지 결정하는 일이다. 초기 가설은 “작은 팀에서는 버그를 등록하는 일보다 재현에 필요한 정보를 다시 묻고, 수정 완료와 검증 완료를 구분하는 일이 자주 누락된다”이다. 실제 사용자 인터뷰로 확인된 사실은 아니다.

사용자:

- 제보자: 발견한 문제와 재현 환경을 기록한다.
- 개발자: 재현 방법을 보고 수정하고, 수정 내용을 남긴다.
- 검증자: 지정된 버전에서 다시 확인하고 통과·실패를 기록한다.

이것은 작업상의 역할이다. 시스템 권한은 별도로 Owner / Member / Viewer 세 가지만 사용한다. Member가 제보·개발·검증을 모두 수행할 수 있으며 별도 QA 조직을 가정하지 않는다.

### 대표 시나리오

1. 민수가 “모바일에서 로그인 버튼 두 번 누르면 오류”를 Inbox에 등록한다.
2. 환경과 실제 결과만 작성했으므로 카드에 “재현 단계·기대 결과 필요”가 표시된다.
3. 지연이 부족한 정보를 채우고 `간헐적 재현`, 발생 조건, 심각도, 우선순위를 정해 Ready로 옮긴다.
4. 담당자를 정하고 In Progress로 옮기면 민수 화면에도 변경이 반영된다.
5. 같은 버전을 열어둔 다른 사용자의 수정은 충돌 안내로 처리한다. 입력한 내용은 남는다.
6. 수정 설명과 확인할 앱 버전을 기록하고 Verify로 옮긴다.
7. 재검증 통과 기록이 생기면 Done으로, 실패하면 실패 이유와 함께 In Progress로 돌아간다.

## 2. 기존 도구와의 차이

| 도구 | 공식 문서에서 확인되는 기능 | ReproBoard의 설계 초점 |
|---|---|---|
| Notion | 작업 DB, 상태·담당자·기한, 스프린트·보드 | 재현 정보 누락과 재검증 조건을 기본 흐름으로 제공 |
| Trello | 카드·보드, 커스텀 필드와 체크리스트 등 | 버그 양식·준비 조건·검증 결과를 사용자가 처음부터 조합하지 않아도 됨 |
| Linear | 트리아지 인박스, 수락·중복·거절·보류, 우선순위 설정 조건 등 | 기능 경쟁을 주장하지 않고, 작은 범위의 버그 검증 흐름을 직접 실행·분석할 수 있는 공개 프로젝트로 구현 |

Notion·Trello도 설정·템플릿·자동화로 유사한 흐름을 구성할 수 있고, Linear는 이미 강한 트리아지 기능을 제공한다. 따라서 “기존 도구로 불가능한 기능”이라고 주장하지 않는다. 위 비교를 바탕으로 선택한 **버그 전용 기본 UX와 검증 가능한 협업 구현**이 이 프로젝트의 포지셔닝이다.

출처: [Notion 작업 DB·스프린트](https://www.notion.com/help/sprints), [Trello 커스텀 필드](https://support.atlassian.com/trello/docs/using-custom-fields/), [Linear 트리아지](https://linear.app/docs/triage). 모두 2026-09-13 확인.

### 차별점 세 가지

**① 재현 준비 상태가 보이는 카드**

재현 단계·기대 결과·실제 결과·실행 환경을 구조화한다. 작성 여부를 `재현 정보 3/4`처럼 표시하고 빠진 항목을 바로 알려준다. 이 수치는 **필드 충족 수**이며 실제 재현 성공률·버그 신뢰도·품질 점수가 아니다. 재현 여부는 사람이 별도로 기록한다.

**② 수정과 검증이 분리되는 완료 조건**

코드 수정 후 Verify에서 재검증한다. 검증 환경·앱 버전·결과·메모를 기록해야 Done으로 이동한다. 실패하면 원인 메모를 보존하며 다시 작업한다. 임의 점수나 AI 판단으로 버그를 자동 종료하지 않는다.

**③ 협업 중의 상태를 이해할 수 있는 화면**

즉시 반영된 카드에는 저장 중 표시가 붙고, 실패·충돌·연결 문제를 서로 다른 안내로 보여준다. 개발자 관점에서는 실제 DB의 버전 검사와 테스트가 그 동작을 뒷받침한다. “실시간”이라는 표시만 켜둔 시연을 완료로 인정하지 않는다.

## 3. MVP 범위

### 반드시 완성하는 핵심

| 기능 | 2주 구현 범위 | 수용 기준 |
|---|---|---|
| 버그 양식 | 제목, 재현 단계, 기대·실제 결과, 환경, 재현 상태, 심각도, 우선순위, 담당자 | 필드·전환 조건을 프론트와 DB 명령 양쪽에서 검사 |
| 칸반 | Inbox / Ready / In Progress / Verify / Done 고정 | 상태 간 드래그 이동 및 키보드로 사용 가능한 이동 메뉴 |
| 완료 흐름 | 수정 메모·검증 기록·실패·재오픈 | 검증 없는 Done을 직접 API 호출로도 차단 |
| 낙관적 UI | 카드 상태 이동을 먼저 화면에 반영 | 명확한 실패 시 해당 이동만 취소, 다른 카드 변경 유지 |
| 충돌 | 같은 이슈의 정수 version으로 동시 수정 감지 | 한 요청 성공·다른 요청 충돌, 로컬 초안 보존 |
| 실시간 | 이슈·댓글·활동·본인 알림 변경 알림을 받아 최신 데이터 조회 | 서로 다른 로그인 세션 2개로 확인 |
| 재연결 | 끊김/동기화 중/정상/일부 연결 실패 표시, 최신 스냅샷 재조회 | 끊긴 동안의 변경 복구, 오프라인 쓰기 자동 적재 없음 |
| 권한 | Owner / Member / Viewer + 워크스페이스 격리 | DB 직접 호출의 허용·거부 테스트 |
| 협업 진입 | 워크스페이스 생성, 단일 사용 초대 링크, Member↔Viewer 변경 | 다른 사용자 실제 참여·읽기 권한 체험 가능 |
| 로그인 | GitHub OAuth 1종, 로컬 개발 전용 테스트 사용자 | 실제 OAuth 수동 확인과 개발 계정 테스트를 구분 |
| 댓글·멘션 | 일반 텍스트, 같은 팀 사용자 선택 멘션, 댓글 기반 인앱 알림 | 자기 자신·팀 외 사용자 제외, 같은 요청의 중복 알림 방지 |
| 활동 기록 | 생성, 필드 변경, 상태 이동, 검증을 DB 트랜잭션에 기록 | 실패한 명령의 성공 로그가 남지 않음 |
| 검색·URL | 제목/이슈키 검색, 심각도·우선순위·담당자 필터, 정렬, 상세 선택 | 새로고침·복사·뒤로가기 후 동일 화면 상태 |
| 사용성 | 로딩·빈 목록·검색 결과 없음·오류·권한 없음·모바일 | 주요 흐름 키보드 사용, 포커스 복귀, 오류 재시도 |
| 공개 문서 | 실행 가이드, 설계, 테스트 결과, 한계, 라이선스, 시연 | 새 clone에서 기록된 절차로 실행 가능 |

원안의 실시간 공동 편집은 **이슈 단위 공동 수정**으로 구체화한다. 같은 텍스트 위치를 동시 편집하는 Google Docs 방식은 포함하지 않는다.

### 일정 지연 시 먼저 줄이는 항목

1. 멘션 자동완성·알림 UI → 일반 댓글과 활동 기록 유지.
2. OAuth 외관·부가 프로필 → GitHub 로그인 동작만 유지. 외부 설정이 막히면 미검증으로 공개.
3. 초대 링크 UI → 로컬 setup script로 3명의 테스트 멤버를 구성하고 제약 공개. 실제 팀 운영용 완성도는 낮아짐.
4. 공유 URL과 기본 필터를 유지하며 고급 필터 조합·장식·추가 테마 제거.
5. 공개 배포 → 로컬 실행 가이드와 실제 영상으로 대체.

축소 시 PRD·ACCEPTANCE·README에 변경한 범위를 기록한다. 제외된 기능을 완료로 소개하지 않는다. **동시 수정·롤백·실시간 복구·권한·핵심 흐름·최소 증빙**은 포트폴리오의 핵심이므로 마지막에 급히 삭제하지 않는다.

### 후속 개발

- 같은 열 안에서의 수동 순서 변경, 자유로운 상태·필드 편집.
- 중복 버그 추천·통합, AI 요약·자동 우선순위.
- 이미지·영상 업로드, Slack/GitHub 양방향 연동, 이메일·푸시 알림.
- 커서 공유, 타이핑 표시, CRDT/OT 기반 텍스트 공동 편집.
- 오프라인 변경 큐·자동 병합, 무한 스크롤, 전체 데이터 대규모 검색.
- 대시보드·스프린트·결제·모바일 앱·조직 관리자 콘솔.

## 4. 화면 설계

| 화면 | 주요 내용 | 인터랙션·예외 |
|---|---|---|
| 로그인/시작 | GitHub 로그인, 내 워크스페이스, 생성·초대 수락 | 로그인 취소·만료된 초대·미설정 안내 |
| 보드 | 필터, 연결 상태, 5개 상태 열, 카드 | 드래그·상태 이동 메뉴, 저장 중, 0건, 요청 실패 |
| 버그 상세 패널 | 재현 정보, 분류·담당자, 수정·재검증, 댓글·활동 | 미저장 초안, 충돌 비교, 포커스 복귀 |
| 팀/알림 | 초대 링크, 멤버 역할, 내 멘션 알림 | 권한 거부, 만료·중복 수락, 읽음 처리 |
| 샘플 보기 `/demo` | 합성 데이터의 읽기 전용 보드 | “샘플 데이터” 명시, 실제 협업 기능은 로그인/영상 안내 |

데스크톱은 작업 밀도가 높은 보드, 모바일은 선택한 상태의 목록과 전체 화면 상세를 사용한다. 상태를 색상에만 의존해 전달하지 않는다. 긴 제목·한글 입력·카드가 없는 열·좁은 화면을 D4부터 확인한다.

## 5. 기술 구성

| 기술 | 맡기는 책임 | 선택 이유 |
|---|---|---|
| Next.js App Router + TypeScript | 라우팅·페이지 경계·인증 콜백·React UI | 기존 경험 활용, 서버/클라이언트 경계 설명 가능 |
| TanStack Query | 서버 데이터 캐시, 조회·변경 수명주기, 재조회 | 저장 데이터의 단일 소유자 |
| Zustand | 여러 컴포넌트가 공유하는 임시 UI 상태 | 드래그 대상·패널 UI 등에 제한적으로 사용 |
| URLSearchParams | 검색·필터·정렬·선택된 이슈 | 공유·새로고침·브라우저 탐색 일관성 |
| Supabase Auth / Realtime / PostgreSQL | 로그인, DB, 변경 알림, RLS | 직접 WebSocket 서버·인증 서버 구축 범위 축소 |
| PostgreSQL RPC | 권한·전환 조건·버전 검사·기록을 한 트랜잭션으로 처리 | 프론트 로직만으로 막을 수 없는 경쟁 상태 해결 |
| DnD 라이브러리 | 드래그 제스처 | 호환되는 안정 버전 1종 선택, 이동 메뉴 함께 제공 |
| Zod + React Hook Form | 입력 검증·폼 | 복잡한 버그 양식과 오류 안내 |
| Vitest / Testing Library / Playwright | 순수 규칙·UI·두 사용자 실제 흐름 검증 | 위험에 맞춰 테스트 계층 구분 |

버전 번호를 문서 작성 시점의 기억으로 고정하지 않는다. D1에서 공식 문서와 실제 설치 환경으로 호환성을 확인하고 package.json·lockfile·Node 버전을 고정한다. 직접 WebSocket 서버, Prisma, Redis, GraphQL은 추가하지 않는다. 프론트의 Zustand에 이슈 배열을 복제하지 않는다.

기술 근거: [Next.js 서버·클라이언트 경계](https://nextjs.org/docs/app/getting-started/server-and-client-components), [TanStack 낙관적 업데이트](https://tanstack.com/query/latest/docs/framework/react/guides/optimistic-updates), [Supabase Realtime](https://supabase.com/docs/guides/realtime/postgres-changes), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security). 구현 세부 설계는 이 문서에서 선택한 프로젝트 계약이며 라이브러리가 자동 보장하는 기능이 아니다.

## 6. 완료 판정

아래는 목표이며 현재 측정·실행 결과가 아니다.

- 핵심 수용 기준 AC01~AC16 중 릴리스 필수 항목이 모두 검증되었거나, 정직하게 축소된 범위에서 재정의되어 있다.
- 두 사용자 시연에서 정상 이동 → 충돌 → 오류 → 재연결 → 검증 완료까지 직접 보인다.
- 깨끗한 clone과 새 로컬 DB에 문서의 명령만으로 실행할 수 있다. GitHub OAuth의 수동 외부 설정은 별도 표시한다.
- 제품 흐름을 막는 결함, 권한 누출, 수정 손실, 무한 로딩을 남긴 채 “MVP 완료”라고 하지 않는다.
- README 첫 화면에서 목적·화면·실행 방법·기술적 핵심·한계를 알 수 있다.
- 실제 결과를 가진 테스트 보고서, 기술 사례 3개, 3~4분 시연 영상, 주요 화면 캡처가 있다.
- 작성자가 “왜 Query와 Zustand를 나눴는지”, “실패한 이동이 다른 카드에 영향을 주지 않는 이유”, “동시 수정이 DB에서 어떻게 거부되는지”를 설명할 수 있다.

## 7. 성능과 외부 피드백

성능 목표는 합성 데이터 100개, 동시 사용자 2명, 기록된 로컬 환경에서 정한다. 인터랙션과 동기화 시간을 측정할 때 응답 지연·브라우저·빌드 모드·표본 수를 함께 남긴다. 예: 낙관적 이동은 서버 응답 전 시각적으로 반영, 정상 네트워크에서 변경 전파 2초 이내를 초기 목표로 측정한다. 이는 서비스 수준 보장이나 실제 운영 성과가 아니다.

조회는 워크스페이스 최대 500개 이슈를 MVP 대상으로 제한한다. 전체 수가 범위를 넘으면 잘린 결과를 정상 전체 결과처럼 보여주지 않는다. 제한 안내를 표시하며 페이징은 후속 과제로 남긴다.

D12에 지인 개발자 1~2명에게 “버그 등록, Ready 전환, 재검증 완료”를 직접 시켜볼 수 있으면 좋다. 관찰한 어려움 2~3개만 개선한다. 참여자가 없다면 자기 검증이라고 기록하고 사용자 테스트를 했다고 쓰지 않는다. 수집한 제보·화면은 동의를 받고 식별 정보를 제거한다.

## 8. 포트폴리오 배치

이 프로젝트에 2페이지를 배정한다면 첫 페이지는 문제·작동 화면·본인 역할·핵심 흐름, 두 번째는 동시성/낙관적 UI/재연결 중 가장 좋은 사례 2개와 검증 증거를 넣는다. “React·Next·Zustand 사용”만 나열하지 않는다.

각 사례는 **문제 → 고려한 방법 → 선택 → 실제 검증 → 남은 한계** 순서로 쓴다. 수치가 없으면 구체적인 동작과 테스트 결과로 설명한다. AI 활용은 “Codex로 구현·테스트 초안을 작성하고, 범위·상태 계약·실패 사례를 직접 결정·검증했다”처럼 실제로 한 역할만 적는다.

세부 로그·파일 출처는 GitHub 문서에서 연결한다. 포트폴리오 화면 아래에 테스트 파일명이나 출처 주석을 빽빽하게 넣지 않는다.
