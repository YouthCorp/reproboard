# 프론트엔드 포트폴리오 사례

상태: 작성 양식. 결과·수치·역할을 미리 완료형으로 채우지 않는다.

## 프로젝트 요약

- 기간: 실제 시작/종료일
- 개발 형태: 개인 프로젝트, 실제 협력자가 있으면 역할 명시
- 목적: 재현 정보와 재검증 조건이 연결된 버그 협업 UI
- 본인 역할: 직접 수행한 범위만
- Codex 사용: 코드·테스트 초안/디버깅/문서 등 실제 사용 범위
- 구현·배포·시연 링크: 실제 존재하는 링크만

## 실제 개선 사례 — 있으면 추가

관찰한 사용자 행동 또는 실제 결함 → 원인 → 수정 → 검증. 참여자가 없으면 자기 조작 점검이라고 명시한다. 전후 성능은 같은 조건에서 측정했을 때만 적는다.

## 포트폴리오 2페이지 구성

| 페이지 | 내용 | 분량 |
|---|---|---|
| 1 | 한 줄 문제·본인 역할·실제 보드·핵심 제품 흐름·사용 스택 | 화면 약 절반, 설명 4~6문장 |
| 2 | 가장 좋은 기술 사례 2개·짧은 검증 결과·한계·GitHub/영상 | 사례별 문제/선택/검증 3~4문장 |

상세 테스트 파일명·증거 출처를 포트폴리오에 작은 글씨로 나열하지 않는다. 본문에는 설명에 필요한 근거만 두고 상세는 GitHub 문서로 연결한다.

## 검증 완료 후 사용할 수 있는 표현의 틀

아래 문장은 해당 구현·검증이 끝난 경우에만 실제 사실로 채택한다.

- “서버 데이터와 요청 중 UI를 분리해 카드 이동을 즉시 반영하고, 실패 시 해당 이동만 취소하도록 구현했습니다.”
- “이슈 version을 DB에서 검사해 동시 수정을 감지하고, 충돌한 사용자의 입력을 보존하는 화면을 구현했습니다.”
- “서로 다른 로그인 세션에서 변경 전파·수정 충돌·재연결 복구를 검증했습니다.”

“사용자 생산성 40% 향상”, “실시간 데이터 손실 0%”, “동시 사용자 수천 명 지원”처럼 측정되지 않은 성과를 넣지 않는다.

## 면접에서 답할 질문

1. 이슈를 Zustand에도 넣으면 어떤 문제가 생기는가?
2. 카드 이동의 낙관적 성공과 서버 저장 성공은 어떻게 구분하는가?
3. 보드 전체 snapshot rollback의 반례를 설명할 수 있는가?
4. SELECT 후 일반 UPDATE만 하면 경쟁 상태를 막을 수 있는가?
5. 응답을 못 받았는데 서버는 성공한 경우 재시도는 어떻게 처리하는가?
6. Realtime 재구독 성공만으로 최신 데이터라고 할 수 있는가?
7. Viewer 버튼을 숨기는 것과 DB 권한 검사는 어떻게 다른가?
8. Codex가 작성한 코드 중 본인이 어떤 설계와 검증을 책임졌는가?
