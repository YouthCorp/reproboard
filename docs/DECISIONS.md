# 기술 결정 기록

## ADR 01 — 낙관적 이동을 서버 값과 분리

- 상태: 제안
- 문제: 카드 A의 실패 때 보드 전체 이전 스냅샷을 복원하면 B 또는 다른 사용자의 성공 변경을 잃을 수 있다.
- 고려한 방법: 전체 snapshot rollback / 캐시의 이슈별 변경·복구 / 서버 캐시와 요청별 overlay 분리.
- 계획된 선택: 서버 캐시+overlay, 같은 이슈 로컬 pending 1개.
- 장점: 실패한 요청의 임시 상태만 제거하고 최신 서버 값을 유지하기 쉽다.
- 비용: overlay와 원격 업데이트의 순서·version을 일관되게 처리해야 한다.

## ADR 02 — 이슈 단위 version 충돌

- 상태: D4 Inbox 필드까지 구현. 실시간 협업은 D7에서 확장.
- 문제: 두 사람이 오래된 이슈 내용을 저장할 때 조용히 덮어쓸 수 있다.
- 고려한 방법: 마지막 저장 우선 / 편집 잠금 / 정수 version 조건부 수정 / CRDT.
- 계획된 선택: expectedVersion을 DB에서 검사하고 충돌 시 초안 보존.
- 장점: 2주 범위에서 수정 손실을 감지하고 사용자 선택을 제공한다.
- 비용: 서로 다른 필드 변경도 충돌하며 자동 병합을 제공하지 않는다.
- 실제 구현 파일: `supabase/migrations/20260914000100_d2_issue_commands.sql`, `20260916000100_d4_issue_fields.sql`, `src/features/issues/issue-form.tsx`.
- 실제 반례/검증: `tests/db/commands.test.mjs`의 다른 필드 동시 수정 성공 1/충돌 1, `tests/db-ui/board.spec.mjs`의 두 사용자 초안 유지·명시적 최신 반영 후 재제출. `fields.spec.mjs`는 재조회 성공/실패에서 본문 초안을 보존하고 최신 값 선택 시만 교체됨을 실제 DB로 확인한다. TEST_REPORT D4 참조.
- 결과와 남은 한계: 행 잠금 후 expectedVersion 검사로 제목·본문의 조용한 덮어쓰기를 막았다. 요청 receipt와 실제 변경은 원자적이다. 실시간 이벤트 순서·오프라인 응답 유실의 전체 복구는 아직 검증하지 않았다.

## ADR 03 — 변경 알림과 재조회로 복구

- 상태: 제안
- 문제: 연결이 끊겼다가 돌아오면 그동안의 변경 이벤트를 놓칠 수 있다.
- 고려한 방법: 이벤트만 직접 캐시에 적용 / 변경 알림→재조회 / 사용자 정의 재생 가능한 이벤트 로그.
- 계획된 선택: Postgres Changes를 재조회 신호로 사용, 재구독 후 최신 스냅샷 확인.
- 장점: 클라이언트의 복잡한 이벤트 재생 범위를 줄인다.
- 비용: 추가 조회가 발생하고 네트워크 복구 후 잠깐 동기화 대기가 필요하다.
